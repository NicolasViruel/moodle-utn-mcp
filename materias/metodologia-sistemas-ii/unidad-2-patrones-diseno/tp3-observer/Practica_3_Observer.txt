¿Qué está pasando en el proyecto? 
Tenemos un sistema de inventario. Cada vez que el stock de un producto baja, hay que 
notificar a tres sistemas: alertas por email, el panel de analytics y el módulo de reposición 
automática. El developer original lo hizo directo. Muy directo. 
El código problemático 
CLASE InventoryManager: 
  CONSTRUCTOR: 
    this.emailService   = NUEVO EmailAlertService() 
    this.analytics      = NUEVO AnalyticsDashboard() 
    this.replenishment  = NUEVO AutoReplenishment() 
  
  MÉTODO update_stock(productId, quantity): 
    this.stock[productId] = quantity 
    SI quantity < 10: 
      this.emailService.send_low_stock_alert(productId, quantity) 
      this.analytics.record_low_stock_event(productId) 
      this.replenishment.trigger_order(productId, 100) 
  
  MÉTODO sell_product(productId, sold): 
    this.stock[productId] -= sold 
    SI this.stock[productId] < 10: 
      this.emailService.send_low_stock_alert(productId, ...) 
      this.analytics.record_low_stock_event(productId) 
      this.replenishment.trigger_order(productId, 100) 
 
El problema de fondo 
El InventoryManager conoce por nombre a EmailAlertService, AnalyticsDashboard y 
AutoReplenishment. Si cualquiera de los tres cambia, o si querés agregar notificaciones 
push, tenés que abrir el InventoryManager. Que no tiene nada que ver con emails ni con 
analytics. Eso es acoplamiento. 
¿Qué hace el patrón Observer? 
El InventoryManager mantiene una lista genérica de "cosas que quieren saber cuando algo 
cambia". Cuando el stock baja, recorre la lista y avisa a cada uno. No sabe quiénes son — solo 
sabe que tienen un método onLowStock(). Cada observador decide qué hacer con el aviso. 
Anclaje teórico 
Observer (también llamado Observador, Publicación-Suscripción, Event-Subscriber, Listener) 
es un patrón de diseño de comportamiento que define un mecanismo de suscripción para 
notificar a varios objetos sobre cualquier evento que le suceda al objeto que están observando. 
La estructura canónica del patrón identifica tres roles principales: 
• Notificador (Publisher): Envía eventos de interés a otros objetos. Mantiene el campo 
de suscriptores y los métodos subscribe/unsubscribe/notifySubscribers. 
• Interfaz Suscriptora: Declara la interfaz de notificación. Consiste típicamente en un 
único método update con parámetros de contexto. 
• Suscriptores Concretos: Realizan acciones en respuesta a las notificaciones. 
Implementan la misma interfaz para que el notificador no esté acoplado a clases 
concretas. 
En este ejercicio, InventoryManager juega el rol de Notificador, StockObserver es la Interfaz 
Suscriptora, y EmailAlertObserver/AnalyticsObserver/ReplenishObserver son los Suscriptores 
Concretos.

Pseudocódigo de la solución 
1. La interfaz del observador 
INTERFAZ StockObserver: 
  MÉTODO onLowStock(productId, quantity) 
 
2. Cada servicio implementa la interfaz 
CLASE EmailAlertObserver IMPLEMENTA StockObserver: 
  MÉTODO onLowStock(productId, qty): 
    enviar email "Stock bajo: " + productId 
  
CLASE AnalyticsObserver IMPLEMENTA StockObserver: 
  MÉTODO onLowStock(productId, qty): 
    registrar evento en el dashboard 
  
CLASE ReplenishObserver IMPLEMENTA StockObserver: 
  MÉTODO onLowStock(productId, qty): 
    crear orden de reposición por 100 unidades 
 
3. El manager solo conoce la interfaz 
CLASE InventoryManager: 
  CONSTRUCTOR: 
    this.observers = []        // lista vacía, sin nombres concretos 
  
  MÉTODO subscribe(observer: StockObserver): 
    this.observers.agregar(observer) 
  
  MÉTODO unsubscribe(observer: StockObserver): 
    this.observers.remover(observer) 
  
  MÉTODO notify(productId, qty):        // privado 
    PARA CADA observer EN this.observers: 
      INTENTAR: 
        observer.onLowStock(productId, qty) 
      SI FALLA:                         // DENTRO del loop 
        registrar el error 
        CONTINUAR con el siguiente      // no detiene la cadena 
  
  MÉTODO update_stock(productId, qty): 
    this.stock[productId] = qty 
    SI qty < 10: 
      this.notify(productId, qty) 
 
Truco clave — dónde va el manejo de errores 
El bloque de captura de errores debe estar DENTRO del loop, envolviendo cada llamada 
individual. Si está FUERA: el primer observer que falla corta toda la cadena. Si está 
DENTRO: cada observer es independiente — uno puede fallar sin afectar a los demás.
